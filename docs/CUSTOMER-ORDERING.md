# Angular Guest QR Ordering and Tracking — G2 / Issue #5

This increment closes the missing **frontend-to-real-API path** from a table
Ordering QR to guest menu, modifiers, bounded cart, server-priced checkout and
Order-scoped tracking. It does not create any payment request or bank QR.

## Routes and APIs

- `/order#token=<43-character-visit-secret>`: the table's Ordering URL is
  issued by `POST /api/tenants/:tenantId/stores/:storeId/tables/:tableId/rotate`.
  The guest page extracts the exact fragment and **immediately removes it
  from browser URL/history** with replaceState before any API request. No
  query-string token or log/analytics exposure. It sends the secret in the
  JSON body of `POST /api/guest/ordering-visit/resolve`. It neither requires a
  customer account nor allows cross-store/menu access.
- Available products, categories, option groups and available modifiers come
  from the visit resolver; sold-out items are not shown. Guest can search and
  filter by category, choose group-bounded add-ons, and add multiple unique
  product+option combinations. Cart is limited to 20 lines, 100 units and 20
  units per line, matching Backend validation.
- Cart value is explicitly labelled **estimated/not paid**. No client amount
  is sent at checkout. The page re-resolves the active visit before creating
  an Order; if availability/options or estimated satang change, it blocks
  checkout until guest reviews the updated cart. The Backend still enforces
  the authoritative Order price, available products, group constraints,
  snapshots and concurrency policy in PostgreSQL.
- `POST /api/guest/orders` sends only `visitToken` and bounded
  `{productId,optionIds,quantity}` lines plus an unpredictable
  `Idempotency-Key` generated by `crypto.randomUUID()`. A same-cart
  network retry reuses the **same key** while the current in-memory cart is
  unchanged. A deliberate cart edit resets the key. Multiple rapid clicks
  are disabled while submitting. A 404 revoked QR rejects checkout; no
  orders are submitted to another table automatically.
- After HTTP 201 success the server's Order ID, amount (integer satang),
  status and order-only bearer `trackingToken` replace the estimate.
  `/order/track` uses `Authorization: Bearer <trackingToken>` with
  `GET /api/guest/orders/:orderId/status` and `/history`, displays a Thai
  timeline and refreshes every 15 seconds when visible/online. It does not
  expose staff actor IDs or other customers' Orders.
- The tracking bearer is stored only in **same-tab sessionStorage** (maximum
  12 hours) and the in-memory Angular service. It is never placed in URL,
  localStorage, network logging or shared cross-tab state. After closing
  the tab or storage expiry the customer may lose tracking access. This is
  a constrained interim browser recovery model, not equivalent to server-
  controlled HttpOnly session storage; avoid third-party scripts, enforce
  CSP and minimize XSS attack surface. The table's ordering token remains
  in memory only. Reloading the menu requires rescanning the Ordering QR.

## Client states

| Adverse state | Behavior |
| --- | --- |
| Missing/malformed QR | Explicit rescan message; never guess tenant/store |
| Revoked, expired or forged visit | HTTP 404, clear in-memory visit, request new QR |
| Network / 5xx resolve error | Preserve token in memory for explicit retry |
| Sold-out item/option | API hides from menu; server rejects stale cart |
| Missing mandatory modifier choice | Block add-to-cart before checkout |
| Catalog/price changed during review | Re-resolve and require new confirmation |
| Double click, ambiguous network timeout | Stable in-memory idempotency key, no optimistic success |
| Another table or rotated visit | Server denies checkout; no cross-visit reuse |
| Tracking token missing/expired | No status leakage; prompt a new scan/order |
| Payment not yet built | Explicit `not_requested`, no paid label or live PromptPay QR |

## Local development

Run `pnpm dev:api` with **development-only auth** and test database;
`pnpm dev:customer` serves Angular with an `/api` proxy to
`127.0.0.1:3000`. Configure the API's exact
`AUTH_ALLOWED_ORIGINS` to include the customer browser origin and set
`GUEST_ORDER_BASE_URL` to that origin's `/order` path. The API must
still enforce Origin on all POST calls, including guest ordering; do not
remove Origin validation to facilitate local development. Use HTTPS and
appropriate credential configuration in staging; this is not permission to
deploy a public ordering service. `/api/ready` intentionally remains 503
until non-payment security, auth and release gates are qualified.

- Existing PostgreSQL/HTTP tests verify server Order prices/snapshots,
  idempotent concurrent retries, stale table tokens, role isolation and
  Order tracking capabilities. The customer page uses those endpoints.
- **Still required for full Issue #5 completion:** mobile **browser E2E**

  review of sessionStorage under the final CSP/hosting design.
- Payment/PromptPay per **Order** stays explicitly deferred to G5 (#7),
  after merchant/reporting/reliability/staging work. An Ordering QR is not
  a payment QR.

## G2 cart re-confirmation guard (8 Nov 2026; #5/#38)

Checkout no longer compares only total satang after re-resolving the guest
visit. Even an unchanged grand total must trigger customer review when a
selected product is renamed/recategorized/repriced, a selected option is
renamed/repriced/removed, a relevant Modifier group's label/min/max changes,
or the table/visit changes. Two offsetting price updates **must not cancel
each other out** as a false match. The page preserves the cart and displays a
Thai re-confirmation notice; it never sends a changed item without review.
PostgreSQL still validates and snapshots all selected items and amounts.

Vitest covers same-total rename/offsetting deltas, new mandatory Modifier
groups, removed options and cross-visit/table changes. This does not add
a Payment state, QR payment or Checkout-time stock reservation.

## G2 large-menu progressive rendering and offline tracking qualification (8 Nov 2026)

The Customer menu now filters the **server-provided menu snapshot** using the
existing Thai search/category semantics, but initially mounts only 24 product
cards; `แสดงเมนูเพิ่มเติม` mounts the next 24. Any search/category change
resets the visible batch. A live result count and 48px accessible button
preserve navigation on a 320px screen. Cart and PostgreSQL checkout remain
authoritative and are independent of how many cards happen to be visible.

The Order-tracking page now shows an explicit offline/stale-state warning,
disables manual refresh while offline, and fetches fresh server status when
connection/visibility returns. It never queues a speculative Order mutation
or marks Payment verified. Chromium CI exercises 320px search/overflow and
offline tracking/reconnect; Vitest exercises 70-product Thai filtering.

**Scope limit:** This is client DOM batching, **not** server-side Guest catalog
pagination, transfer-size optimization or measured real-device bandwidth.
Physical printed-QR/weak-network/screenreader and large-catalog staging
performance remain open G2 acceptance gates.

## Server-paged Guest menu and shared API budgets (8 Nov 2026; G2/#38)

Guest browsing now uses `POST /api/guest/ordering-visit/page` and 24-product
server-side keyset pages. Category and debounced Thai search are applied
inside PostgreSQL and issue fresh page requests; subsequent pages are fetched
only on demand. A previously reviewed cart line keeps its item and Modifier
snapshot across filter/page changes. Checkout's full re-resolution and
transactional order engine still reject stale/changed items or prices;
a partial page is not the authority to place an Order.

All public guest resolve, printed-code redemption, catalog page, checkout,
and tracking endpoints use atomic HMAC-anonymized shared PostgreSQL rate
budgets (fixed per-peer and per-token lanes). Explicit HTTP 429 responses
tell clients to retry later. The previous per-Visit failed-code cap remains.
See [G2 Guest paging and budgets](G2-GUEST-PAGING-AND-BUDGETS.md) for limits,
SQL/HTTP tests, ingress NAT caveats and the daily maintenance requirement.

The old full Guest resolver remains for backward compatibility and cart
reconfirmation; physical mobile/printed-QR, production edge rate limits and
large-store load evidence are still outstanding. No Payment or Production.
